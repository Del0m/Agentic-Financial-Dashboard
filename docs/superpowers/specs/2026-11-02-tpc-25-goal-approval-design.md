# TPC-25: Goal approval in the UI, accepted goals become budget lines

Date: 2026-11-02. Status: implemented. Verification is in the [manual verification handoff](../../handoffs/2026-11-02-tpc-25-manual-verification.md).

Ticket: [TPC-25](https://ucf-ctcw-senior-design.atlassian.net/browse/TPC-25), epic TPC-5 (M4). Branch: `TPC-25`, cut from `origin/main`, which has TPC-23, TPC-24 and TPC-32 merged.

## Goal

From the ticket: `POST /goals/generate`, `POST /goals/{id}/accept`, a Goals view, approval via `interrupt()`, and an accepted goal becoming a budget line (e.g. "Debt payoff: $300/mo").

**Done when:** accepting a goal shows it on the dashboard and in next month's budget.

**Out of scope:**
- running the goal graph automatically after period close (section 4 of the architecture says "later");
- a preferences form (`--prefs` stays the way to set them);
- tracking what the user actually paid toward a goal;
- editing a proposed goal's amount;
- TPC-31's forecast, which later replaces the measured surplus.

## Decisions

Rows marked **confirm** are the design's own defaults, not something the user has chosen yet.

| Decision | Why | Alternative rejected |
|---|---|---|
| **Confirm:** each goal is accepted or dismissed on its own | A proposal can hold three goals, and the user may want only the first. Every accepted set fits, because the whole proposal fit the cap | All-or-nothing, which makes the user reject a debt plan over a savings line they don't want |
| **Confirm:** a goal joins the budget at the next close, or in the first budget if none exists yet. The month under way never changes | The ticket says "next month's budget", and budget styles already apply this way. A goal's plan starts on the 1st of next month | Adding a line to the open month, which cuts Free mid-month |
| **Confirm:** a goal line shows the planned amount with no spent figure, pace or flag | Nothing reliably measures contributions: card payments aren't spending and a transfer can't be tied to a goal. "$0 of $583" would be wrong | A pace bar on a number that's always $0 |
| **Confirm:** an accepted goal can be stopped with `POST /goals/{id}/dismiss`; its line ends at the next close | Otherwise one wrong click commits money for years, with no way back | No undo |
| **Confirm:** a goal proposal expires at the close that opens its start month (a December proposal expires when November closes), or when a first budget opens on that month, like `adjust_next_budget` proposals | The surplus behind a proposal goes stale. Accept never has to recheck affordability | Revalidating at accept time, which needs a second path through the validation code |
| **Confirm:** new proposals are capped by `max(round(surplus × max_share) − accepted goals' monthly amounts, 0)`, and a kind with an accepted goal isn't offered | Two runs can't commit the same money twice. One line per kind keeps `(period, category)` unique | Superseding accepted goals on regeneration |
| A run writes nothing if the accepted goals changed while it ran (`error`, reason `goals_changed`), and accepting is refused while a goal of that kind is accepted | A decision takes no lock, so a user can accept during a model call. Without this the cap is committed twice, and two lines of one kind make every later close fail with an `IntegrityError` that close reads as "another close got there first" | Holding the user's lock for decisions, which blocks a click for a whole run |
| **Confirm:** in 50/30/20, goal lines come out of the saving target: `saving = max(target − goal lines, 0)`. If goals pass the target and the lines pass income, `_split` raises `over_income` | Paying down debt and building savings are what the 20% is for. Free and needs are left alone, and the user is told when it doesn't fit | Goals on top of the 20%, with the total rising silently |
| Goal lines use a new `goal` group and reserved categories `GOAL_DEBT_PAYOFF`, `GOAL_EMERGENCY_FUND`, `GOAL_SAVINGS` | Groups are plain strings, so no migration. Close, pace and the transaction picker need one check to treat them apart | Reusing `saving`, where every saving line reports the same total |
| The `caps` style needs no new rule: goal lines count as planned, so Free shrinks by exactly the goal | Goals are funded from the surplus and never cut another line. If the lines pass income, the existing `over_income` alert fires | |
| Rows are the source of truth, as for alerts. `interrupt()` tracks the run, and a decision commits before any resume | A failed resume or a lost checkpoint never loses a click, and close reads rows, so a paused run can't block a budget | Applying the decision inside the resumed graph |
| Goals generated by the CLI don't pause, but can still be accepted in the app | The CLI has no checkpointer. `decide_goal` only resumes a run if one is paused | Blocking the CLI on input |
| Paused checkpoints hold no debt names, balances or model text, only the aggregate figures the run summary already stores: a `forget_facts` node clears the rest, and `durability="exit"` stops earlier steps being written | Debt names and balances would otherwise sit in the checkpoint file. Tested on langgraph 1.2.18: with `sync` the secret reached disk, with `exit` it didn't, and resuming twice still worked | The default durability, which writes every step |
| Add `goals.start_date` (nullable) | `created_at` is the wall clock, which is wrong for a simulated user. Close needs the plan's real first month | Deriving it from `created_at` |
| A row with no `start_date` can't be accepted (409) | Rows from before this ticket may be over the cap or undated, and TPC-24 says they aren't certified | Accepting them |
| Close completes an accepted goal once its `target_date` month has passed: status `completed`, no more line, and one `goal_ended` alert on the new period (medium, no category): "Your {name} goal reached its planned end date, so its {amount} budget line has ended. Check that it's done, and generate goals again if there's more to do." A goal the user stopped gets none | Free comes back and the kind can be offered again. Status is a plain string, so no migration. Nothing tracks contributions, so without the alert Free rising could be read as "debt done" | Lines that run forever |

## Double counting

Three places would count one dollar twice. The first two share one rule: only the amount **above the line's old limit** is attributed to the goal.

`net_of_goal(actual, limit, goal) = actual − min(goal, max(actual − limit, 0))`

Subtracting the whole goal would be wrong. Avalanche usually sends a debt goal to a card, whose payments aren't in `LOAN_PAYMENTS`. A $200 goal would turn an unchanged $210 loan payment into a $10 line, cancel the goal's effect on Free, and raise `over_limit` every month after.

1. **Saving line.** A fixed line adopts its actual at close, so a goal's transfer would inflate `SAVINGS_TRANSFER` and be budgeted again by the goal line. `gather_month` nets `saved` against the closed month's `emergency_fund` and `savings` goal lines.
2. **Loan spending.** The same applies to `LOAN_PAYMENTS` and a `debt_payoff` line, in both `gather_month` and `evaluate`. Otherwise paying the goal to a loan looks like overspending, or lands on Free when the user has no loan line. It could also lead the model to propose a limit that includes the goal.
3. **Regeneration.** The cap subtracts accepted goals. **Known limit:** once the user's transfers show up in history, the measured surplus has already fallen, so the amount is subtracted twice and the cap is understated until the goal ends, and for a few months after it, because the surplus is a three-month median that still holds the goal's payments. This errs on the safe side, and TPC-31's forecast replaces this figure.

## Lifecycle

```text
proposed --accept--> accepted --target month passed, at close--> completed
    |                    |
    |                    +--dismiss ("stop")--> dismissed
    +--dismiss--> dismissed
    +--new proposal, withdrawal, or the close that opens its start month--> superseded
```

```text
load_facts -> propose -> validate_candidate -> persist -> forget_facts -> await_approval -> END
                 ^               |                                |
                 +-- correction -+                                +-- nothing stored (goals_changed, a failed run): END
                                  (await_approval loops on interrupt() until no row is proposed)
```

With a checkpointer, every end that doesn't raise passes through `forget_facts`, including a withdrawal and a stop before `persist`. Only a run that stored goals goes on to `await_approval`. Without one (the CLI), every end goes straight to `END`: there is no `forget_facts` or `await_approval`, nothing reaches disk, and the run doesn't pause.

An `AgentRun` is `running`, then `awaiting_user` while paused (no lock held, and `running_elsewhere` ignores it), then `ok`. The code that resumes the graph writes the final row, as `run_goals` does today. If the checkpoint is lost, the run is finished from the rows once none is `proposed`. A paused run whose proposals were superseded or expired becomes `expired`. `close_interrupted_runs` only touches `running`, so a paused run survives a restart. Close can't reach the checkpointer, so an expired run's checkpoint stays behind; it holds no debt names, balances or model text, only the aggregate figures the run summary already stores, so this is harmless.

## API

```text
GET  /goals?status=proposed|accepted|current  default proposed, so TPC-23's contract holds. current = proposed + accepted
POST /goals/generate { date? }  -> 202 { run_id }; 409 if a run is going for this user
GET  /goals/runs/{id}           -> { run_id, status, outcome, reason, goal_ids, waiting_for, attempts, issues, error }
POST /goals/{id}/accept         -> GoalOut; 404 other user's; 409 already decided, superseded ("This proposal expired. Generate goals again.", `GoalExpired`), no start_date or target_date, or a goal of that kind is accepted
POST /goals/{id}/dismiss        -> GoalOut; 404, 409. Works on proposed and accepted
```

`GoalOut` gains `start_date`. `waiting_for` is read from rows, so a lost checkpoint doesn't break the page. A run takes tens of seconds and the Next.js proxy drops a request after 30 s, so generate runs in a background thread and the page polls, as `POST /budget/run` does.

## UI

- **`/goals`:** a Generate button with a status line, the proposal as cards with Accept / Dismiss, and accepted goals with a Stop button.
- **Dashboard:** a Goals card listing accepted goals and the month each joins the budget, plus a Goals link in the header showing the proposal count. A failure stays inside the card.
- **Budget card:** a goal line reads "Debt payoff: $583.00/mo" with no meter.
- **Transaction picker:** goal lines aren't offered, and `PATCH /transactions/{id}` refuses them (422). A goal line has no spending to hold.

## Risks

| Risk | Handling |
|---|---|
| A user accepts between `gather_month` and `persist_month` | The answer stands and the line arrives one month later. Rare, and it self-heals |
| The cap understates after contributions start | Conservative, documented above, replaced by TPC-31 |
| The debt goal's date assumes the user pays | The line ends on the projected date even if the debt remains. Without contribution tracking, nothing can tell. Documented in the handoff |
| A run is paused when the user regenerates | `_supersede` marks it `expired` and deletes its checkpoint after the commit |
